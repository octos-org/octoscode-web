# 自托管产品发布复核：以完整工作流程为主线

目标由用户确认：**个人或可信团队连接自己的 Octos
Core**。本轮不增加公开多租户托管、账号体系或独立运行时。检查基于 Web `bd4408b`
后的工作树；GitHub 读取到 24 个开放 issue，数量只用于核对遗漏，不作为产品质量分数。

## 发布判断的方法

产品需要让人可靠完成“连接自己的 Core
→ 打开项目 → 发起工作 → 审批或回答问题 → 离开当前会话 → 回来看结果 → 继续下一轮”。按当前实现和实际运行判定，不沿用 issue 的旧 P1/P2 标签，也不以是否采用某个库作为上线门槛。

| 完整场景           | 准入要求                                                                               | 本轮处理及证据范围                                                                                                |
| ------------------ | -------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 第一次连接         | 地址可理解；允许未启用认证的 Core；等待有界且可取消；凭据不跨身份混用                  | 保留可选 token 和浏览器可观测错误的排障文案；补 15 秒握手超时、迟到回调与重试隔离                                 |

## Bug 与体验分别记录

本轮修复的可靠性问题：

| Bug                                       | 用户可见后果                                                        | 修复方式                                                                                                                                      |
| ----------------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 静默 WebSocket 握手没有截止时间           | 连接一直等待，重试状态可能受到旧回调影响                            | 15 秒超时，并隔离被替换连接的迟到回调                                                                                                         |
| 未发送草稿只在内存中                      | 普通刷新丢失输入                                                    | 同一标签页、同一认证身份、按会话保存，恢复时不发送                                                                                            |
| 草稿删除或保存失败后误清 dirty 状态       | 空输入或切换空会话后失去离开提醒，刷新可能出现旧草稿                | 持续提示失败，并在确认写回成功前保留离开保护                                                                                                  |
| 浏览器拒绝存储删除时假装 Forget 成功      | 刷新可能恢复旧连接、凭据和草稿                                      | 每个 key 删除后读回核验，连接前后均提示未清理成功；不把浏览器异常伪装为成功                                                                   |
| Workspace recents 读写未完整隔离存储异常  | 只读存储时 Forget 中途抛错，界面没有反馈                            | 保持当前内存工作区列表可用，将清理结果纳入失败提示                                                                                            |
| 草稿缓存达到上限时静默淘汰旧草稿          | 保存第 51 份输入会挤掉先前未发送文字                                | 保留已有 50 份和当前输入，阻止会丢失当前输入的切换；发送，或先复制再清空当前输入后继续                                                        |
| 新 canonical hydrate 未消费及线程重排     | 新 Core 保留的原始输入/部分输出可能不显示，多线程问题与回答顺序改变 | 验证成对扩展字段、凭唯一消息身份关联背景子线程、合并完整 durable 正文与附件，新增恢复行遵循全局事件顺序，既有正文保持原阅读顺序；旧 Core 兼容 |
| 完整 hydrate 后接受早于快照的迟到 live 帧 | 已恢复的时间线可能追加过期事件                                      | 新完整快照设定 cursor 下界；保留旧 Core 部分 lane 原有规则                                                                                    |

体验改进另列：后台完成/待输入提醒、diff 语法与词级阅读、同 tab 草稿恢复体验。工具历史身份关联、正文层级和暗色动效沿用上一轮已交付修复，本轮在真实已保存会话上回归。

仍有价值的体验工作：完整服务器会话目录、会话间阅读位置/折叠记忆、对话搜索、全局快捷入口、真正辅助技术实测。它们没有被假装为 bug 或已完成；下方附录分别说明当前可行入口和未承诺范围。没有为此引入新编辑器、状态库、锁系统或动画框架。

## 对旧 issue 判断的校正

- **空 token 并不天然是 bug。**
  Core 支持可选认证，强制 token 会破坏合法连接。浏览器 WebSocket `error`
  也不能可靠区分认证拒绝与网络失败，因此不伪造具体原因。
- **缺少 Web Locks 不等于双运行 owner。**
  rc.9 已在服务端互斥区拒绝同会话的并发 turn/start；只有真正启动工作的连接才登记 owner。关闭纯旁观窗口不会终止另一个连接的任务。因此本轮没有新增一套浏览器锁系统。
- **旧 owner 清理仍有真实版本风险。**
  A 完成 T1、B 开始 T2 后关闭 A 的旧连接，是不同于“纯旁观”的场景。Core main 的
  [#2268](https://github.com/octos-org/octos/pull/2268) 已加入 dispatch
  identity 检查；部署 rc.9 和已发布 rc.11 不包含该修复。前端继续保守保留 owner，不冒充已根治 Core 生命周期。
- **手动定位工作区和已保存链接是有效的受控入口。**
  它们不能提供完整服务器会话目录，但“没有完整目录”也不等于“已有工作完全无法打开”。错误作用域结果必须继续拒绝。
- **断线续跑是一项单独的产品能力。**
  当前 Core 为 attached 执行；有明确离开预警、准确终态与保留历史的 attached 模式可以作为受控使用契约。未持久化输入/部分输出无法从旧 Core 找回，是仍然存在的数据恢复缺口，不能仅用警告文案判定已解决。

## Core 版本与发布边界

部署端仍为 rc.9，本轮没有自动升级共享 Core 服务。rc.11 也不具备 detached turn
lease 或完整 scoped catalog。Core main 的
[#2296](https://github.com/octos-org/octos/pull/2296) 增加有界 canonical
replay 与 thread
checkpoint；本轮 Web 现在能正确消费这些字段，但旧服务器不会因此凭空产生历史。

为避免技术提案变成无限改造，分清两层承诺：

1. **当前受控自托管范围**：同一活跃标签页工作、已完成会话恢复、已保存引用打开、明确的连接/存储失败提示，以及经测试的审批和编辑流程。
2. **完整断线续跑与跨设备工作台**：需要 Core 的 detached
   lease、生命周期清理与权威 Workspace/Session catalog。相关上游
   [#2167](https://github.com/octos-org/octos/issues/2167)、[#2146](https://github.com/octos-org/octos/issues/2146)
   仍需交付及端到端验收。

当前 rc.9 的未持久化内容丢失和特定旧 owner 清理风险，必须保留在发布说明中。若上线承诺包含断网、刷新后工作完整继续，则这两条仍是阻塞条件；不能据前端 CI 通过宣布该能力达标。

### 验证中的失败与限制

首轮跨浏览器测试错误地期待默认 mock 持久化新生成回复；该 fixture 实际返回固定 transcript。修正为分别验证实时回复、fixture 已有持久历史与草稿恢复后，两种浏览器全部通过。真实 Core 的历史恢复另列证据，不用固定 mock 冒充新回复持久化。首轮同时编辑模块时的 Firefox
Settings 等待失败也在冻结后的干净运行中复核通过。

独立复审在新增 canonical 恢复中发现了过期 live 帧、父子线程身份及无锚点交错顺序问题，均在最终检查前修复并补回归。只读存储下的 Forget 中断来自实际 App 浏览器操作；容量测试通过预置 50 份草稿，验证第 51 份不会淘汰旧输入，并验证 Disconnect 后返回原会话仍能找回输入。

Playwright 的桌面浏览器和窄屏尺寸不等同于真实手机、VoiceOver 或 NVDA 验收。桌面通知通过受控 Notification
API 测试显式授权、拒绝、重复与清理；不同操作系统的实际通知呈现仍由浏览器负责。

发布判断：前端按当前受控自托管流程验收；完整断线续跑、跨设备目录和旧 Core 尚未保留的历史不在通过声明中。附录中的未完成产品能力继续开放；过时事实或已交付事项才关闭。
