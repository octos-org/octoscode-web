# 会话切换与交互性能复核

2026-09-15。针对实际反馈：切换 Session、打开 Settings/Models、发送消息迟缓；绿色完成状态不随当前会话正确显示；点击会话触发排序。

此前的小会话、短文本和流式输出检查不足以证明长代码历史可流畅使用。本轮在生产构建上用 Playwright 和 CDP 做了修复前后对比，确认主线程同步高亮是明显瓶颈。

## Bug 与修复

- 长历史首次渲染 200 条记录，每个代码块在屏幕外也同步高亮；加载任一语法还会使所有代码块重新计算。240 条消息的代码场景中，切换一次会话产生超过 8 秒的单个长任务，CPU 采样主要落在高亮正则匹配。现在仅接近视口的代码块高亮，按当前语言的就绪状态更新，移除零延迟定时器预加载三种语言。全文仍能阅读、复制。
- 打开设置、输入等 App 更新会重新遍历 Timeline，并重新读取/解析整个标签页连接与草稿存储。现在 Timeline 有独立 memo 边界，自动连接偏好只初始化一次；草稿保存时机不变。
- General/Models 子模块挂起会连同设置壳一起消失。现在加载提示位于内容区，已出现的导航和关闭按钮可继续使用；模块加载失败仍由既有 SurfaceBoundary 隔离。
- 当前会话完成状态仅依赖后台 owner，冷恢复的 completed 状态也未提供给侧栏。现在 live
  terminal 与 hydrate 使用一致的明确终态字段，选中会话优先使用自身状态；hydrate 依 Core 已保证的 turns 生命周期顺序选择当前状态，较早失败不能覆盖较新完成。没有添加本地任务结果缓存或凭 assistant 文本猜状态。
- 恢复历史时，旧回合的失败/停止提示统一追加在整段历史末尾。现在按服务端回合顺序放在后续回合之前，避免出现在新回复下面。
- 延迟高亮实测会替换代码滚动容器，横向位置从 200 归零。现在使用 Shiki
  inline 输出并保留同一个 pre；验证高亮前后 scrollLeft 均为 200，高度均为 48px。
- 打开会话更新 lastOpenedAt，注册表和工作区随后重排。现在默认固定顺序，已有项留在原位，新会话插到顶部；容量淘汰仍按真实 LRU。用户可主动选择 Last
  opened 等排序。

## 体验调整

首次展示最近 40 条消息，较早历史仍按既有入口每次展开最多 100 条，保留阅读锚点。切换 Settings 或编辑输入不会重新处理整段历史。没有引入虚拟列表框架、全局高亮缓存或 React
Compiler。

## 性能证据

基线为 `ccdc69a`。同机 Chromium、1440×1000、生产构建、CDP
4 倍 CPU 限速；240 条消息、120 个历史回合，每个 assistant 含 120 行 TypeScript。通过已有 fixture 的 hydrate 响应注入完整历史，RPC 仍经过实际前端客户端。每次会话切换重新 hydrate，未用缓存页面代替。

| 操作                              |         修复前 |                  修复后 |
| --------------------------------- | -------------: | ----------------------: |
| 4 次会话切换的操作等待范围        | 8,832–8,927 ms |              428–459 ms |
| 上述切换中的最大单个主线程长任务  |       8,379 ms |                  145 ms |
| 冷打开设置的操作等待              |      10,441 ms |                  444 ms |
| 冷打开设置观察窗口内最大长任务    |       3,566 ms | 未出现超过 50 ms 的任务 |
| 发送消息的操作等待                |         843 ms |                  160 ms |
| 打开设置/模型时标签页存储读取次数 |    每次 1–2 次 |                    0 次 |

不加 CPU 限速时，修复后 4 次会话切换为 158–175 ms，发送为 64
ms；首次设置/模型内容仍有约 0.8 秒模块/RPC 等待，但设置加载壳可操作。冷加载和受限设备仍会出现短长任务，本轮没有宣称全部操作达到固定延迟。

操作等待由 Playwright 点击到目标就绪及两次动画帧计算，包含自动化定位与等待开销，**不是 INP**。长任务来自浏览器 PerformanceObserver，CPU 归因来自 CDP
Profiler。共享主机负载会影响绝对值；这里报告同一场景的实测结果，不外推到所有 Core、网络或用户历史。方法参考
[Chrome Performance](https://developer.chrome.com/docs/devtools/performance/reference)
与 [交互延迟分解](https://web.dev/articles/optimize-inp)。

## 验证与限制

- Playwright 实际检查：延迟 General 内容加载时切换 Models、选择模型、关闭后不重开；反复切换两个会话保持顺序，Completed/Failed 与当前会话一致；旧失败不覆盖较新完成；高亮保留代码横向滚动。
- 既有 360 消息浏览器场景继续验证展开历史、阅读锚点、流式输出、代码复制、窄屏及会话切换重置窗口；仅适配初始条数，没有增加测试 case。
- 单元测试数量维持 496（client 112、web 384），仅调整已有状态/排序断言。
- `pnpm check`
  全部通过；68 项既有浏览器回归通过。CI 与部署状态在本次 PR 中记录。
- 真实 Core 的只读小历史探测不能代表用户完整长历史；压力数据为合成代码历史。Core/RPC 本身的耗时、断线恢复边界没有被这个前端修复消除。

本机详细证据：`/tmp/octos-interaction/`，包含 before/after JSON、CPU
profiles、临时探测脚本与检查日志；临时脚本没有加入常规单元测试套件。
